# Decisions

Rulings made while building faultline, in the format
`- Ruling: <what> — <why> — <cost if wrong>`.

## Scope and stack

- Ruling: Go standard library only, plus `go.yaml.in/yaml/v3` for experiment files — the proxies, control API, metrics and CLI are all expressible with `net`, `net/http`, `httputil` and `flag`, and a small dependency surface suits a tool that sits in the data path — if a richer CLI or metrics stack is wanted later, the hand-rolled flag parsing and Prometheus text writer would need replacing.
- Ruling: one process (`faultline serve`) owns every proxy and is driven over a JSON HTTP control API; the CLI and the experiment runner are both clients of that API — the same guard rails (allowlist, TTL caps, kill switch, audit) then apply no matter who injects a fault — an experiment runner that wanted to inject without a daemon would have to start one in-process (the tests do exactly that).
- Ruling: the bundled sample system is a TCP "pricing" line-protocol backend plus an HTTP "catalog" API that calls it with a 250 ms timeout — a two-hop dependency chain is the smallest system where L4 faults on the back hop surface as L7 errors and latency on the front hop, which is what makes the demo experiments meaningful — the sample is deliberately small and has no retries or caching, so it fails faster than a production service would.
- Ruling: no datasets, so no `DATA.md` — every number comes from loopback traffic generated by the tests, the demo and `tools/latencybench` — none.

## L4 proxy

- Ruling: the TCP relay reads into timestamped chunks and a separate writer releases each chunk at `arrival + latency` — latency then delays bytes without serialising them, so a latency fault does not also cut throughput (a naive `sleep; write` per chunk would) — memory per direction is bounded by `queueDepth × chunkSize` (64 × 32 KiB); a slow consumer blocks the reader, which is the intended back-pressure.
- Ruling: jitter never reorders bytes (a chunk's due time is clamped to the previous chunk's) — TCP is an ordered stream; reordering would corrupt data rather than simulate jitter — under heavy jitter on a busy stream the effective delay is skewed upwards, as on a real link with a FIFO queue.
- Ruling: probability, source scope and `max_affected` are decided once per connection, not per chunk — a 30 % fault should break 30 % of connections, not 30 % of the packets of every connection — per-packet loss is not modelled (see Limitations).
- Ruling: RST is produced with `SO_LINGER=0` on close; `close` is a FIN after N bytes; `slow_close` holds the half-close for a delay; `blackhole` drops bytes but keeps the socket open — these are the four distinct ways a peer can disappear that client code handles differently — no packet-level faults (loss, duplication) because faultline is a user-space proxy, not a netem replacement.
- Ruling: bandwidth caps use a pacer that writes `rate/20`-byte slices and does not accumulate burst credit while idle — keeps throughput within a few percent of the cap at 50 ms granularity (see benchmarks) — a token bucket with burst would model some links better.

## L7 proxy

- Ruling: HTTP faults apply in a fixed order: delay, then abort, then status, then forward with body corruption — a deterministic order makes combinations predictable (e.g. a delayed 503) — users cannot reorder them.
- Ruling: every faulted response carries `X-Faultline-Fault: <ids>` — injected failures must always be attributable when someone debugs them later — a service that echoes unknown headers would leak the fault ids to its clients; aborted connections cannot carry the header.
- Ruling: bit-flip corruption draws the gap to the next corrupted byte from a geometric distribution — cost is O(flips) instead of O(bytes) with the same per-byte probability — none.
- Ruling: `abort` hijacks and RSTs the client connection; on HTTP/2 it panics with `http.ErrAbortHandler`, which resets the stream — the closest equivalent per protocol — HTTP/2 clients see a stream reset rather than a TCP reset.

## Engine and control plane

- Ruling: the fault registry is a copy-on-write slice behind an `atomic.Pointer` — proxies read it on every chunk and request, writes are rare — each write copies the slice (≤ 32 faults per proxy by default).
- Ruling: the upstream allowlist defaults to loopback only and every resolved address must be inside it; TCP upstreams are pinned to the resolved IP at creation — a fault injector that can be pointed at arbitrary hosts is an SSRF and blast-radius risk, and pinning prevents a later DNS change from redirecting traffic — staging use needs `--allow-upstream`; HTTP upstream host names are not pinned (TLS/virtual hosting need them), so a DNS change after creation is not re-checked for HTTP.
- Ruling: every fault has a server-side TTL; faults without one get `--max-ttl` (default 30 min) and longer TTLs are refused — a fault must never outlive a crashed or forgotten client — long soak experiments need `--max-ttl` raised.
- Ruling: `serve` refuses to bind a non-loopback address unless `FAULTLINE_TOKEN` is set, and the token is read from the environment, never a flag — a reachable, unauthenticated fault-injection API is a denial-of-service button; flags leak into `ps` — single shared bearer token, no per-user identities or RBAC.
- Ruling: the control API refuses browser-originated requests: an `Origin` header or a `Sec-Fetch-Site` other than `none` gets `403`, a POST whose `Content-Type` is not `application/json` gets `415`, and, when no token is set, a `Host` that is not a loopback IP or `localhost` gets `421` — review found that a cross-origin `text/plain` POST (a CORS simple request, sent with no preflight) from any web page could create a proxy on `0.0.0.0`, and DNS rebinding could also read responses; faultline's CLI, runner and curl send none of these headers, so nothing legitimate breaks — browser-based tooling (a future web UI) would need an explicit allowed-origin option; a client that strips `Origin` would bypass only the first check.
- Ruling: `Origin` is refused even when a token is set, but the `Host` check applies only without a token — a browser cannot attach the bearer token cross-origin, so with a token DNS rebinding gains nothing, and checking `Host` would break legitimate remote use behind a name; the `Origin` refusal costs nothing because no supported client is a browser — none.
- Ruling: proxies may only listen on a loopback address (a literal loopback IP or `localhost`; `0.0.0.0`, `:port`, LAN IPs and other names are refused) unless `serve --allow-public-listen` is given — creating a proxy to an allowed loopback upstream on a public interface publishes that service to the network, and the upstream allowlist cannot see this — sharing a proxy with another host now needs a daemon flag.
- Ruling: on shutdown the daemon engages its kill switch before closing — no fault outlives the process that enforces its TTL — none (proxies stop with the daemon anyway).
- Ruling: the audit log is an in-memory ring of 512 events — enough to explain a run, no storage dependency — history is lost on restart; ship it elsewhere via `GET /v1/audit?since=N` if it must be kept.

- Ruling: `probability` and corrupt `rate` are optional pointers (`*float64`), not zero-valued floats — with a plain float an explicit `probability: 0` was indistinguishable from "omitted" and was silently widened to 1 (every connection faulted), and `rate: 0` became 0.01; omitted still means 1 and 0.01 — Go callers write `fault.Float(0.3)` instead of `0.3`.
- Ruling: an explicit `probability: 0` is honoured, not rejected: the fault is registered, audited and listed with `p=0` but never applies — it is the safe direction (smaller blast radius), it matches the documented 0–1 range, and it allows a staged or disabled arm — a typo of 0 for 1 produces a fault that does nothing, which is visible in `fault ls` and the report.
- Ruling: an explicit corrupt `rate` of 0 is rejected (a flip fault that never flips is a mistake), and `rate` with `mode: truncate` is rejected instead of being ignored — fields that cannot take effect must fail loudly — none.

## Experiments

- Ruling: experiments are YAML decoded through JSON with unknown fields rejected — a typo such as `abrot:` must fail loudly instead of silently dropping a guard rail — YAML anchors/merges work but YAML-only types do not.
- Ruling: `${VAR}` / `${VAR:-default}` expansion is applied to the raw file and an unset variable without a default is an error — lets one experiment target dev and staging ports without templating tools — `$` followed by `{` cannot appear literally in a file.
- Ruling: fault TTLs in experiments are derived (`step duration + safety.fault_ttl_grace`) and a hand-written `ttl` is rejected — if the runner dies mid-step, the server removes the fault shortly after it was due to end — none.
- Ruling: rollback runs on its own context with a 15 s budget, after any outcome (completion, abort, Ctrl-C, step failure) — cancelling an experiment must never skip cleanup — a control API that is down during rollback leaves faults until their TTL expires (which is why TTLs exist).
- Ruling: verdicts map to exit codes (0 passed, 2 failed, 3 aborted, 4 precondition failed, 1 error) — experiments can gate CI pipelines — none.
- Ruling: probe samples are attributed to the phase in which they *started*, except that a probe sent just before injection and answered during it counts as a fault-phase sample; phases are re-summarised after probing stops — requests in flight across a boundary were exposed to the faults, so counting them as steady state produced false "not recovered" verdicts in the first build of the demo — the fault phase is diluted by up to one probe interval of unaffected samples at its start.
- Ruling: a success-rate abort objective fails only when the one-sided Wilson upper bound (default 95 %) of the observed rate is below the objective (`abort.confidence`, 0 = point estimate) — with the point estimate, 3 failures out of 5 samples under a 20 % fault aborted the demo's "falsified hypothesis" experiment by chance; the bound keeps hard outages fast (0/4 against 0.8 aborts) while ignoring noise — low objectives need more samples to prove a breach (0/n against 0.3 needs n ≥ 7); latency abort objectives still use point percentiles.
- Ruling: the abort window is time-based (`abort.window`) but is extended back to the most recent `min_samples` samples when it holds fewer — during a timeout-heavy outage probes take longer than the probe interval, so a short time window could never collect enough samples and the abort check starved (found by the abort-on-breach test: the run went the full 30 s) — the effective window during outages is longer than configured.
- Ruling: steps of the schedule run concurrently at their `at` offsets; the method phase ends when the last step ends or on abort — overlapping faults are the interesting case — no dependencies between steps beyond time offsets.
